# Dynamic DeFi red-team sweep — escrow_program + prop_amm_program (2026-09-19)

Authorized owner-run sweep. Both targets were deployed as **real SBF artifacts** (`target/surfpool/examples/{escrow_program,prop_amm_program}.so`) onto an offline Surfnet via `pina_test::ProgramTest::start_with_artifact`, and attacked through raw instructions built byte-for-byte (discriminator + migration version byte + payload). Scratch attack crate retained at `tmp/sweep/defi-attacks/` (25 probes, all green: `cargo test --manifest-path
tmp/sweep/defi-attacks/Cargo.toml -- --ignored --test-threads=1`).

- Scope: `examples/escrow_program/src/lib.rs`, `examples/prop_amm_program/src/lib.rs` on branch `security-sweep-2026-09-19` (cut at `feat/abi-version-reset` @ `3f7d38f9`).
- Wire formats used: Make `[01 00 | seed u64 | amount_a u64 | amount_b u64 | bump u8]`, Take `[02 00]`, Initialize `[00 00]`, Update `[01 00 | price u64]`, RotateAuthority `[02 00 | new_authority 32]`. Escrow state layout 123 bytes: `[01 00 | maker 32 | mint_a 32 | mint_b 32 | amount_a 8 | amount_b 8 | seed 8 | bump 1]`.

## Findings

### D1 — CONFIRMED — prop_amm's static `UPDATE_AUTHORITY` private key is recoverable from a 1-byte-guessable seed (full price control)

1. **Location**: `examples/prop_amm_program/src/lib.rs:37-40` (constant), gates `assert_update_authority` at `:105-111`, enforced in `Update` at `:156-157`.
2. **Mechanism**: `UPDATE_AUTHORITY` is a hardcoded pubkey. Brute-forcing the harness's deterministic keypairs shows it is exactly `solana_keypair::Keypair::new_from_array([7u8; 32])` — i.e. the ed25519 seed is the uniform byte array `[7; 32]`. Anyone who reads the (public) source can reconstruct the signing key by guessing seeds `[n; 32]` for `n` in 0..=255 (256 tries; ~instant). The guard then compares only addresses, so the reconstructed key satisfies it.
3. **Exploit (executed)**: probe `amm_08_exploit_update_authority_key_recovered` — victim initializes an oracle (authority = victim payer); attacker rebuilds `Keypair::new_from_array([7; 32])`, funds it, and submits `Update([01 00, price=999_999 le], [oracle w, authority=r])` signed **only** by the recovered key. Transaction succeeds; on-chain oracle bytes `34..42` read back `999_999` via RPC. The initializer's key was never used; no rotation involved. The probe asserts both the seed match (`amm_05`) and the on-chain price write.
4. **Severity justification**: the example itself is a benchmark port and comments say the key "matches the Anchor v2 benchmark's hard-coded updater key", so the hardcoding is intentional for a test fixture — but the fact that its secret is trivially recoverable was not documented anywhere, and the example is the template downstream programs copy. Any real program shipped with this pattern has a total oracle/authority compromise (attack cost: read the source). Low as shipped (demo fixture); High if copied. This is a concrete instance of security lesson `11-admin-key-compromise`.
5. **Fix**: (a) never hardcode an authority pubkey whose keypair is derivable from a uniform seed; generate the fixture key from a random seed and commit only the pubkey plus a note that the secret is discarded, or load it from an env/feature-gated test keypair file; (b) add a test that asserts no keypair from uniform seeds 0..=255 (and common patterns like `[0u8;32]..[255u8;32]` slices) matches any hardcoded authority constant — it is cheap and mechanical.

### D2 — CONFIRMED — escrow `Make` can be griefed for any chosen `(maker, seed)` slot by pre-funding the derivable vault

1. **Location**: `examples/escrow_program/src/lib.rs:149` (`self.vault.assert_empty()?`); vault address is the ATA of the escrow PDA (derivable before the escrow exists), created by the ATA CPI at `:180-188`.
2. **Mechanism**: ATA creation never requires the wallet's signature, and the vault's wallet (the escrow PDA address) is computable from public seeds. An attacker can therefore create the vault ATA and transfer any token balance into it **before** the maker's `Make`. `Make` then aborts on `assert_empty` and the escrow is never created. The maker's only recourse is a different `seed`, and the attacker can pre-fund every candidate seed they observe being prepared (front-running is trivial on a public chain).
3. **Exploit (executed)**: probe `escrow_12_prefunded_vault_griefs_make` — attacker runs ATA `CreateIdempotent` with wallet = escrow PDA (no PDA signature needed) plus a raw SPL `Transfer` (tag 3) of 1_000 units of mint A into the vault; the maker's `Make` then fails with "instruction requires an uninitialized account" (program log: `account is not empty`); the escrow account does not exist afterwards.
4. **Severity justification**: Low. No value is stolen — the attacker's deposit stays theirs and the maker loses nothing but the ability to use that seed slot (nuisance DoS). But it is a zero-cost, targeted grief and the empty-check idiom is template code.
5. **Fix**: accept a pre-created vault when it is legitimately empty-for-this-escrow: if `vault` is non-empty, require it to be a token account of `(escrow, mint_a)` under the same token program **with token amount 0** (and no delegated/frozen state) instead of rejecting outright; alternatively create the vault with `create_account` + `initialize_account` owned by the escrow so a pre-created ATA is simply tolerated.

### D3 — CONFIRMED — noncanonical-bump shadow escrow is fully functional on `escrow_program` (second instance of FP1)

1. **Location**: `examples/escrow_program/src/lib.rs:158-164` (`CreateProgramAccountWithUncheckedBump` with instruction-supplied `bump`); Take re-derives the signer from the **stored** bump at `:343-345` and validates seeds with it at `:280`.
2. **Mechanism**: `Make` verifies only `seeds + bump ⇒ submitted address` (`DeriveAndCheck`, `crates/pina/src/cpi.rs:573-598`), never canonicality. Bump 252 (canonical is 255) derives a valid address, so the maker can create a second, parallel escrow for the same `[b"escrow", maker, seed]` namespace with its own vault ATA. `Take` honors the stored bump, so the shadow escrow completes a full Make/Take round trip.
3. **Exploit (executed)**: probe `escrow_13_noncanonical_bump_escrow_still_consistent` — a wrong-bump Make (bump 251 vs address of bump 255) fails with "Provided seeds do not result in a valid address" (the one check the builder does); a genuine noncanonical Make (bump 252, address `FB3fyQk9djwf6cQs7ruw4i1ZhgDAwSGWJix1RcLjcHAp`) succeeds; stored byte 122 == 252; a subsequent Take pays out and closes the shadow escrow normally.
4. **Severity justification**: Low, and **not a new class** — it corroborates FP1 in `dynamic-framework-probe.md` with a second example. Contained here because the seeds bind the maker and `Make` requires the maker's signature, so a shadow escrow is the maker's own doing; the residual risk is canonical-deriving indexers/clients missing the shadow PDA and the template idiom spreading to programs whose seeds do not bind a signer.
5. **Fix**: same as FP1 — lint `CreateProgramAccountWithUncheckedBump` call sites whose seeds do not bind a required signer; optionally expose `bumpVerification` in the IDL.

### Verified-and-holding (no action)

- **L10 holds**: `Make` with `amount_a == 0` or `amount_b == 0` is refused with `EscrowError::EmptyOffer` (code 2) before any account is created (`escrow_01`).
- **`amount_b == 1` rounding edge**: a maker offering the whole vault for one unit gets exactly that — Take pays out the **measured vault balance**, not `amount_a` (`escrow_02`). This is the maker's own offer terms (documented behavior: "stored amount_a is the measured vault delta"), not a theft vector; an attacker who donates into a live vault only enriches the future taker (`escrow_11`), and cannot capture the donation themselves.

Not applicable to this codebase (prop_amm is an oracle port, not a pool AMM): in-tx price manipulation, slippage bypass, rounding-dust harvest, LP-share inflation, reserve spoofing, LP burn underflow, same-tx create+swap+drain. There are no pools, reserves, or LP tokens — only `OracleState { authority, price }`. Escrow has no cancel instruction, so "cancel after take" double-refund is structurally impossible.

## Lint proposals

1. **Recoverable-authority lint** (from D1): flag hardcoded `Address`/pubkey constants used as authorities whose keypair is derivable from low-entropy seeds. Mechanical check: for each constant, try `Keypair::new_from_array([n; 32])` for `n` in 0..=255 (and per-byte-varying patterns) and fail if any pubkey matches. Could live as a workspace test over all example constants rather than a proc-macro lint.
2. **Empty-check grief lint** (from D2): flag `assert_empty()` on addresses that later instructions derive as ATAs of a PDA; propose the "accept derived-and-zero-balance" pattern instead (fits the existing `04-initialization` lesson).
3. **Canonical-bump lint** (FP1, now corroborated by D3 on a second example): flag `CreateProgramAccountWithUncheckedBump` call sites whose seeds do not bind a required signer.
4. **Check-order note** (minor, from probe 21): `Update` validates the global authority before the oracle account's owner/discriminator, so non-authorities always see `UnauthorizedUpdateAuthority` (code 0) even when the real problem is a wrong oracle account — misleading error attribution for integrators. Type-validate before authority-validate, or document the order.
