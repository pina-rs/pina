# Migration machinery — static security sweep (2026-09-19)

Scope: account/instruction/event migration machinery in `crates/pina/src/migration.rs`, `crates/pina_macros/src/{migration,entrypoint,account}.rs`, and `examples/migrations_program/`. Read against the 2026-09-18 deep-audit verdict ("envelope classification Kani-proven; manifest reads recompute per-version sha256 and physical layout (fail-closed); ledger hash-chained; transitions hash-pinned") to find what it misses. Read-only; no tracked file was modified.

Headline: the prior verdict holds, and the deeper property it does not state is the most important one — **transitions are structurally pure**. A generated transition is `include!`d author code whose only signature is `fn migrate(data: &mut [u8])` (+ `target_size(data)` / `working_size(data, target)` for compact steps). There is no way for a transition to read a sysvar, another account, time, or randomness: semantics are a pure function of stored bytes. That single signature constraint is what makes the permissionless reserved route safe. The findings below are the residue.

---

## Findings

### M1 — CONFIRMED (Low-Medium, design) — the reserved `0xFF` route is permissionless; account authority is never checked

1. **Location**
   - `crates/pina/src/migration.rs:994-1061` — `MigrateAccount::invoke_signed_inner` checks only `assert_writable()?.assert_owner(program_id)?`; no authority concept exists anywhere in the executor.
   - `crates/pina_macros/src/entrypoint.rs:465-497` — `process_migrate` + prelude route `0xFF` before any per-instruction authorization; only `IncorrectProgramId` is checked first.
   - `crates/pina/src/migration.rs:919-933` — `validate_funding_payer`: payer must be writable, must not equal the target, and must be a signer **only when funding > 0**.
   - Example wiring: `examples/migrations_program/src/lib.rs:22-32` (`migrations(State, ManualState, CompactState, State)`).
2. **Mechanism**. Anyone may submit the reserved instruction `[0xFF]` with metas `[anyPayer(sign), systemProgram, victimState]`. The payer can be the attacker. No signature from the victim account's authority is consulted because the framework does not know what an authority is.
3. **Exploit scenario**. Attacker fronts (or gratuitously sends) `0xFF` targeting a victim-owned `State` at v0. Migration runs v0→v1→v2, attacker pays ~7k lamports of rent for the 2-byte growth, account lands at v2 with `enabled=0, revision=0`.
4. **Severity justification**. Low-Medium because the blast radius is bounded by framework invariants: transitions cannot change business semantics (structural purity, see below), cannot move lamports out (only `payer → account` system transfers exist; `apply_migration` touches only data bytes; shrink "retains every lamport"), and the owner's next transaction behaves identically (handlers normalize/migrate on demand). Residual impact: (a) the owner's off-chain tooling pinned to v0 wire breaks at an attacker-chosen moment; (b) the attacker irreversibly locks their own lamports inside the victim's account (no withdrawal path) — self-cost grief only; (c) if a program author _does_ encode meaning in the version envelope itself ("v1 means admin approved"), forced migration becomes a semantic weapon — the framework cannot see that intent, so this stays a standing trap.
5. **Fix**. Keep the permissionless default (it is the crank model and is safe _because_ transitions are pure), but: (i) document the invariant "the reserved route is public; never encode authority meaning in a version number" in `docs/src/migrations/`; (ii) add a `pina_lints` rule on `pina.toml`/handler pairs where a contract's transitions are `manual` and the account name suggests authority semantics; (iii) optionally support `migrations(authority = ...)` opt-in that adds an authority-signer slot to the reserved route for programs that want a gated route.

**Structural mitigations verified** (why this is not High):

- Transition purity is enforced by signature, not convention: `crates/pina_macros/src/migration.rs:237-242, 500-520, 838-858` `include!` the transition files and the generated call sites invoke `migrate(workspace)` / `migrate(destination)` — no context parameter exists to smuggle in.
- Lamports can only flow payer→account (`migration.rs:795-803`); `MigrateAccount`/`MigrateContext` never decrease account lamports; shrink path explicitly retains lamports.
- Program-id checked before any migration (`entrypoint.rs:478-480`; example unit test `reserved_instruction_rejects_a_mismatched_program_id`).

### M2 — CONFIRMED (Low, availability) — `MAX_INLINE_STEPS = 8` permanently strands accounts 9+ versions behind

1. **Location**: `crates/pina_macros/src/migration.rs:1098` (`const MAX_INLINE_STEPS: u16 = 8;`), applied at `:323, :592, :1043` (`max_inline = current.min(8)`); runtime gate `crates/pina/src/migration.rs:1026-1029` (`total_steps > MAX_INLINE_STEPS → MigrationUnavailable`), inline arms `pina_macros/src/migration.rs:266-269` (`MigrationRequired`).
2. **Mechanism**: an account whose stored version is more than 8 below current can neither migrate on the reserved route (`MigrationUnavailable`) nor be normalized inline (`MigrationRequired`), nor pass any current-only loader (`MigrationRequired`). The cap is not configurable in `pina.toml`.
3. **Exploit scenario**: a long-lived program ships v9; every account still at v0 is unrecoverable by any on-chain path for as long as the program lives — a rolling availability trap that compounds with each release.
4. **Severity justification**: Low on-chain (fail-closed, no fund loss; rent still exempted), High annoyance at year three. It is a liveness cliff, not a soundness break.
5. **Fix**: make the cap a `pina.toml` setting with a computed-bounds assert, or generate a chunked deep-ladder (multiple reserved invocations of ≤8 steps each is already possible client-side — document that workaround explicitly: clients drive `[0xFF]` repeatedly and the ladder advances 8 versions per call). At minimum document "compact history before depth 9" in the release checklist.

### M3 — CONFIRMED (Low, accepted design) — post-mutation invariant failures are panics

1. **Location**: `crates/pina/src/migration.rs:663-678` (`abort_after_mutation` → `panic!`), used throughout `complete_step_after_effect` and `finish`.
2. **Mechanism**: after the first effect (funding transfer, resize, or rewrite) a validation failure cannot be rolled back _within the instruction_, so the executor aborts the whole instruction by panicking. Solana rolls the transaction back atomically, so no partial state can commit — this is deliberate and correct; the cost is that an author transition bug presents as an on-chain panic + failed tx rather than a typed error.
3. **Exploit scenario**: none directly; a malformed manual transition turns every migration of affected accounts into a permanent aborting path (accounts stuck stale + always-failing txs).
4. **Severity justification**: Low. Atomicity is preserved; the preflight boundary (`Preflight`/`Mutating` split, `migration.rs:842-913`) is correctly drawn — everything catchable happens before the first effect.
5. **Fix**: none required for the mechanism. Add a `pina migrations verify` host command that replays every transition against generated fixtures so a broken manual transition fails at build/CI time instead of on-chain.

### M4 — CONFIRMED (Low, hardening gap) — the account executor does not zero the grown region before `apply_migration`

1. **Location**: `crates/pina/src/migration.rs:814-820` (`resize(working_size)` then `apply_migration` with no fill of the new region). Contrast the instruction/event path, which zeroes its workspace first (`migration.rs:371`, `:465`).
2. **Mechanism**: on SBF, bytes between the old and new `data_len` after a same-instruction growth are unspecified until the runtime zeroes them at instruction end. Generated transitions write every added byte (e.g. `migrations/transitions/account_1_01/v0_to_v1.rs` `data[42..43].fill(0)`), and destination validation re-validates the full representation — but `validate_migration_destination`/`validate_account_value` only constrains fields that _have_ semantic validation. A hand-written transition that forgets to write an added `u64`/`u8` field bakes account-local residue into persistent, version-stamped state.
3. **Exploit scenario**: author adds `withdrawn: u64` at v3 but the manual transition skips it; account's realloc residue (its own pre-shrink bytes) becomes `withdrawn`. The residue originates from the same account's earlier layouts, so this is stale-data resurrection inside one account, not cross-account injection — but if any earlier layout ever held attacker-written bytes (e.g. a memo field), the attacker may influence the new field's initial value at migration time.
4. **Severity justification**: Low — requires an author mistake, a validation gap on the new field, and favorable residue. The instruction/event path proves the framework knows the right pattern; the account path just never got it.
5. **Fix**: in `complete_step_after_effect` and `first_step`, zero `[old_len..working_size]` of the account data right after the growth resize (bounded by the 10 KiB growth cap, so cheap), making "transition must initialize every added byte" defense-in-depth rather than load-bearing. Add a `pina_lints`/Kani check that every added destination byte range is written by the transition.

### M5 — VERIFIED BENIGN (was attack surface 6) — shrink stale-tail, overfunding, exactness

Blocked/checked, logged so the next audit does not re-derive it:

- **Exact length both directions**: `PinaPodFixed::read_exact` rejects non-exact lengths (test-pinned `crates/pina/src/traits.rs:1440-1448`); planner arms call it before planning; destination arms re-check `data.len()`; `AccountMigrationPlan::try_with_working_size` rejects `working_size < target_size` (`migration.rs:534`).
- **No stale tail survives a shrink**: the executor always resizes down to `target_size` after apply (`migration.rs:821-823`); Solana realloc-down truncates. A compact account with a pre-existing spare tail is truncated to the transition's `target_size` (e.g. `account_1_03` drops the `0xee` spare byte — example test `compact_account_migration_preserves_active_data_and_discards_spare_bytes`).
- **No overfunding path via generated transitions**: funding is the rent deficit at `working_size` (`migration.rs:749-758`); for fixed histories `working = max(source_exact, dest)` so a shrink has `working == current` → funding 0; for compact histories `working = data.len().max(target)` → `working > target` implies `working == current` → funding 0. Surplus retention is therefore unreachable through generated code; only a hand-written `working_size` returning a value above both could overfund — and the surplus still lands in the migrated account, not the attacker.

### M6 — CONFIRMED FIXED on main (prior L6) — width-matched reserved trigger

`crates/pina_macros/src/entrypoint.rs:445-449` selects `is_migrate_instruction_u16/u32/u64` by the enum's primitive, and `crates/pina/src/migration.rs:75-115` makes each helper length-exact (test `reserved_instruction_identification_matches_each_declared_width_exactly`). The 2026-09-18 audit's L6 is remediated in the current tree (`worktrees/fix-migrate-width` @ `9429c2cb` is the same fix). Residual nuance, fail-closed: a program declaring `#[discriminator(u16, entrypoint, migrations…)]` and calling the one-byte `is_migrate_instruction` by hand leaves the reserved path unreachable — the helpers are documented as width-paired.

### M7 — CONFIRMED (Info, supply-chain shape) — transition pinning is mandatory; publications skew is host-side only

- `crates/pina_macros/src/migration.rs:1398-1440` `verify_transition_files`: every version's transition file must exist, must not contain `TODO(pina-manual-manual-migration)` markers in `Manual` mode, and `implementation_sha256.as_deref() != Some(sha256(file))` **fails the build — including when the pin is absent**. There is no "optional pinning" downgrade hole.
- `verify_source_schema` (`pina_macros/src/migration.rs:53-55`) compares the source struct against the manifest's current schema each build; adding/removing/reordering a field without `pina migrations make` is a compile error. `resolve_opt_in` (`:1107-1136`) rejects `migrations = false` on a recorded contract (envelope removal = wire change).
- `migrations/publications.json` (receipt chain: `executableSha256`, `manifestSha256`, `previousReceiptSha256`, per-contract versions) is **host-side deployment bookkeeping** (`pina_cli/src/migrations/ledger.rs`). On-chain behavior is fully determined by the compiled binary plus the manifest embedded at macro expansion (`include_bytes!` + const asserts, `pina_macros/src/migration.rs:116-132`). A stale/skewed publications file cannot change on-chain semantics; worst case it misleads deployment verification UX. Version skew attack: **blocked by construction**.
- Residual (same-repo trust): the pin and the file live in one repo, so any committer can rewrite both in one commit. That is a program-upgrade decision, equivalent to shipping a new .so — acceptable, but worth stating in the guide: transition review is upgrade review.

## Do's and don'ts (draft for the maintainer's guide)

### The framework enforces (you get these for free)

1. **Version envelope integrity**: stale/future/unknown versions are classified before any decode; current-only readers reject stale with `MigrationRequired`.
2. **Exact physical layouts**: every historical and current representation is length-exact and field-validated on plan, per-step, and on destination — before the version marker commits last.
3. **Transition purity**: a transition can only rewrite stored bytes; no sysvar, account, clock, or randomness is reachable from its signature. Semantics are a function of stored state alone.
4. **All-or-nothing ladder**: preflight failures before the first effect are catchable errors; any failure after the first effect aborts the instruction, and Solana rolls the tx back.
5. **Bounded cost**: workspace ≤ 1024 B compile-time assert; account growth ≤ 10 KiB above the pre-instruction size; lamports only payer→account with a declared ceiling; payer must sign when it pays.
6. **One rewrite per account per invocation**: duplicate slots, payer/target alias, foreign ownership, and read-only targets all reject.
7. **Build-time pinning**: transition files are sha256-pinned, TODO-scanned (manual mode), and the source schema is re-verified against the manifest on every compile.

### The framework relies on YOU to uphold (each is a finding candidate if violated)

1. **Never encode authority meaning in a version number.** Anyone can run the reserved route (M1). "v2 = admin approved" is an exploit, not a design.
2. **Never remove or reorder fields, never change a field's type in place** — append-only, additive evolution (the macro re-verifies this against the manifest, but the manifest can be regenerated; history review is the control). Never remove an authority field from a historical schema: the versioned view still exposes it and old accounts still carry it.
3. **Never reuse a discriminator value across versions or contracts.** The `#[discriminator]` enum makes same-enum duplicates a compile error today; cross-contract value reuse is only conventionally avoided — candidate for a manifest lint.
4. **Write every added byte in every transition** (M4). Until the executor zero-fills growth, a skipped field is a stale-data resurrection bug. Prefer `automatic` mode for additive steps; reserve `manual` for repacks and review them like consensus code.
5. **Never let a transition branch on anything but stored bytes.** The signature enforces this today; do not add a context parameter later without a threat-model pass.
6. **Keep histories shorter than the inline budget** (M2): plan history compaction before `current − oldest > 8`, or your oldest accounts strand permanently.
7. **Authorize before you mutate in inline migrations.** The example's `Update` runs `MigrateAccount` before its authority check and is saved only by transaction atomicity — acceptable, but the day someone adds an early `Ok(())` after the migration, it becomes a free-effect gadget. Candidate lint: `MigrateAccount`/`resize`/patch call above an `assert_signer`/authority compare in the same handler.
8. **Treat `manual` transition edits as program upgrades**: both the file and its manifest pin change in one commit; review them together, and run the Surfpool historical suite (see the attack matrix) before shipping.
9. **Do not assume the owner performed a migration**: logs/telemetry keyed on "someone migrated my account" must not gate payouts or state transitions.
10. **Prefer migrating over `try_from_bytes_versioned`** whenever a writable touch is schedulable; the versioned view is a read path for accounts the tx cannot write, and every `match` arm it forces is a place to mishandle an old layout.

### Proposed guards (from this sweep)

- Executor pre-zero of the grown region (M4 fix) — small, closes the only unguarded byte path.
- `pina migrations verify` CI command replaying transitions against generated fixtures (M3 fix).
- `pina_lints`: (a) inline migration before authorization assert; (b) `manual` transition on a contract whose fields suggest authority/ownership semantics; (c) history depth approaching 8.
- Docs: one page stating the permissionless-reserved-route model and the purity invariant in `docs/src/migrations/`.
