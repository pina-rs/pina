# Dynamic Edge Attacks — Sweep 2026-09-19

Red-team executor report for the four example targets, run against real SBF artifacts (`target/surfpool/examples/*.so`) deployed into an offline Surfnet via `pina_test::ProgramTest::start_with_artifact`. Attack crate: `tmp/sweep/edge-attacks/` (five `#[ignore]` battery tests, delete after the sweep). All results below were reproduced tonight on the deployed artifacts.

## Verdict

No exploitable state corruption, aliasing, stale-byte exposure, or validation bypass was found that is reachable from the four programs' public instruction surface. Two findings are recorded, both LOW severity, both in the stored-bump / unchecked-bump family already flagged by deep-audit-2026-09-18 M1 — this sweep adds dynamic, byte-level proof of both mechanisms on real artifacts. Thirty-plus distinct attacks were blocked; the stopping check is named for each in the table below.

## Findings

### F1 — CONFIRMED: stored-bump loader accepts and mutates a shadow Journal at a non-canonical bump (dynamic confirmation of deep-audit M1)

- **Location**: `examples/compact_accounts_program/src/lib.rs:267`, `:311`, `:349` (`Journal::with_stored_bump_pda` at all three mutation paths); loader generated at `crates/pina_macros/src/pda.rs:311-337`.
- **Mechanism**: `with_stored_bump_pda` derives the expected address once from the account's own `bump` field (`seeds + stored_bump`) and compares it to the passed account's address. It never checks the bump is canonical. Any account owned by the program whose stored bump self-consistently derives to its own address passes, so one authority can have multiple live Journals — the uniqueness invariant "one PDA per authority" is not enforced by the loader.
- **Exploit (reproduced)**: fixture battery, `tmp/sweep/edge-attacks` `fixture_battery`:
  1. Host-encode a valid `Journal` with `JournalPatch::new()
     .bump(253).authority(payer).revision(0).title("shadow")` — canonical bump for `[b"compact-journal", payer]` is 254, so 253 is non-canonical.
  2. Install the 66 encoded bytes at `create_program_address([b"compact-journal", payer, 253])` via `ProgramTest::install_historical_account` (owner = program).
  3. Send `Rename` (discriminator 3, version 0, title "SHADOW") signed by the payer: `authority + journal(shadow) + system`.
  4. Result: **instruction succeeds**; on-chain bytes become `...01000000...534841444f57` ("SHADOW"), revision 1. The shadow journal is a fully live second account for the same authority.
- **Severity justification**: LOW as shipped. Reachability through the program itself is closed: `CreateCompactProgramAccountWithBump` verifies `expected_bump == canonical_bump` (`crates/pina/src/cpi.rs:46-59`), and the compact battery re-confirmed non-canonical creation is rejected on the real artifact. No instruction writes the bump field after creation. The shadow therefore requires out-of-band bytes (test fixture, corrupted migration, or a future instruction that stores an arbitrary bump). It is a latent foot-gun: the loader silently blesses such an account if one ever exists.
- **Fix**: this is deep-audit M1's remediation, now with dynamic proof to cite: IDL `bumpVerification` marker distinguishing stored-bump from canonical loaders, plus the rename/lint path. Optionally have compact mutation handlers in the example call `with_checked_pda` (single canonical search) — the example is the framework's showcase.

### F2 — CONFIRMED: `optional_accounts_program::Init` creates a second live store at an attacker-chosen non-canonical bump (create-side unchecked-bump builder)

- **Location**: `examples/optional_accounts_program/src/lib.rs:166-177` (`CreateProgramAccountWithUncheckedBump`), builder at `crates/pina/src/cpi.rs:506-598` (`BumpVerification::DeriveAndCheck`).
- **Mechanism**: the unchecked builder derives `seeds + supplied_bump` once and only checks the passed account sits at that address — any bump whose derivation succeeds is accepted, canonical or not. Later `Touch`/`Inspect` handlers load through stored-bump `load_pda`/`load_pda_mut` (`src/lib.rs:193`, `:227`), which accept exactly the addresses such an account self-consistently derives, so a non-canonical store is a permanent, fully functional second store for the same authority.
- **Exploit (reproduced)**: optional battery, `optional_battery`:
  1. Canonical store: `Init` with canonical bump 253 → `data = 01 00 fd 0000000000000000` (11 bytes).
  2. `Init` again with bump 251 at `create_program_address([b"store", payer, 251])` → **succeeds** (`optional:init-noncanonical-bump OK`), storing `01 00 fb ...`.
  3. `Touch` on the shadow store → succeeds; counter reads 1 independently of the canonical store.
- **Severity justification**: LOW / informational. The source comment (`src/lib.rs:162-165`) documents the accepted risk and its containment is real: seeds embed the authority, every later handler requires that authority to sign, so only the signer's own namespace can be duplicated, and the duplicated counter carries no value. Contrast with the sibling examples: `compact_accounts_program` and `account_realloc_program` both reject non-canonical creation (re-confirmed tonight), so the framework ships two creation builders with opposite guarantees under near-identical shapes — a template-copy hazard.
- **Fix**: keep the builder but make the divergence loud: a clippy/pina lint on `CreateProgramAccountWithUncheckedBump` when the target account declares a bump field, requiring an explicit opt-in (e.g. `#[pina(allow_noncanonical)]`) or switching to the canonical builder. Belt-and-braces: have `Touch`/`Inspect` assert the stored bump equals the canonical bump so a stray shadow is rejected at load time.

## Notes for the record

- Error-code surfaces observed on artifacts: compact custom codes render as `0x1b58`/`0x1b59` (7000/7001); framework `TooManyAccountKeys` renders as custom `0xfffffffe` (i.e. −2). Negative-valued framework codes are distinguishable from user codes by construction, which is useful for client error mapping but worth documenting in the IDL story.
- The optional-slot `None` rule is purely address equality with the executing program (`traits.rs:1112`, `:1131`); meta flags (writable/signer) are irrelevant to the `None` decision, and the program-id filler is accepted in writable form too. Slot-shift between trailing optionals is therefore only as dangerous as the handler validation behind each slot — in this program every `Some` path validates (signer witness, PDA load), so shifting buys nothing.
- `FailsDuplicateMutable` requires no signer at all (distinct writable addresses suffice) — parity-demo semantics, recorded here so the next audit does not re-flag it.
- Fixture evidence (raw bytes) for F1/F2 and blocked stale-byte probes is in the battery output; rerun with: `devenv shell -- cargo test --manifest-path tmp/sweep/edge-attacks/Cargo.toml -- --ignored --nocapture --test-threads=1`

## Lint proposals

1. **Unchecked-bump creation lint**: warn when `CreateProgramAccountWithUncheckedBump` initializes an account type that declares a bump field, unless the module carries an explicit opt-out. Catches the F2 divergence at template-copy time (compact/realloc would pass; optional must opt in).
2. **Stored-bump loader lint / IDL marker** (deep-audit M1 remediation): mark every handler that loads a PDA through `with_stored_bump_pda`/`load_pda[_mut]` and expose `bumpVerification: stored|canonical` in the IDL. F1's dynamic proof is the test case for the lint's rationale.
3. **Duplicate-writable asymmetry doc-lint**: `track_mutable_account` rejects duplicates for `&mut` fields at parse time, while `&AccountView` pairs need the manual `ensure_distinct` pattern (duplicate_mutable example). A lint suggesting `#[pina(remaining, distinct)]` or an explicit distinct-check when two immutable fields share a suffix of seeds would keep hand-ported Anchor parity examples from shipping without the guard.

## Coverage of the attack matrix

Every matrix item was attempted or dispositioned: compact shadow-PDA creation and stored-bump redirect (items 1, 12, F1), spare-byte regions (3, 14), length-confused buffers (5, 6, 34), duplicate compact slots (13), duplicate mutable pairs incl. bump-equivalents (16-22), optional omission/filler/slot-shift (22-29), realloc cap/residual/uninitialized-tail/shrink-grow/close-CPI (30-39). Unverified: none within the matrix; the multi-instruction transaction shape (matrix item 32) is dispositioned by capacity analysis because the codec's 549-byte ceiling makes a >10 KiB cumulative delta impossible for any instruction sequence, and the harness exposes no multi-instruction send.
