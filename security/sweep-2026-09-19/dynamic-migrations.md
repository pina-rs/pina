## New findings

### N1 — CONFIRMED (Low, availability) — the example's lamport cap cannot fund the example's own ManualState ladder; the budget check fires post-effect and panics

1. **Location**
   - `examples/migrations_program/src/lib.rs:12` — `MAX_INLINE_MIGRATION_LAMPORTS: u64 = 20_000`, wired into `#[discriminator(..., migrations_max_lamports = ...)]` and both `MigrateAccount` sites.
   - `crates/pina/src/migration.rs:759-767` — cumulative budget check inside `plan_next_step`; `migration.rs:895` — `Mutating::step` wraps `plan_next_step` in `finish_after_mutation` → `migration.rs:670` `panic!`.
2. **Mechanism**. `mb(6) − mb(3)` = 20,880 lamports (6,960/byte × 3 grown bytes) but the cap is 20,000. Step v0→v1 (6,960) passes the check, funds, resizes, and rewrites — the first effect has landed. Step v1→v2 plans a cumulative 20,880 > 20,000, and because the failure is now post-effect, the typed `MigrationLamportBudgetExceeded` is converted into a program panic. On the real runtime the tx fails with `InstructionError::ProgramFailedToComplete` and rolls back atomically.
3. **Exploit scenario** (availability grief / stranded accounts): any `ManualState` still at v0 can never be migrated — the reserved route and the inline `Update` path (same 20,000 cap) both panic mid-ladder every time, forever. Every attempt costs the victim's client a failed tx; no attacker signature is even needed (any crank that touches the account trips it).
4. **Severity justification**. Low: fail-closed, atomic, no fund loss, and the account stays valid v0 (rent-exempt). But it is a self-inflicted liveness trap in the shipped example: the same pattern (cap < full-ladder deficit) is available to any downstream program that adds two growth steps across versions while keeping a cap sized for one step.
5. **Fix**. (i) Example: raise the cap to at least the full-ladder deficit (≥ 20,880; 24,000 with margin) or drop the cap for the reserved route. (ii) Framework: preflight the **whole-ladder** funding total — sum the deficits of all steps (computable for fixed histories from the layout table before the first effect) so an undersized cap fails with the typed error before any mutation, matching what the shared multi-account budget already does (`reserved_migrate_instruction_shares_one_lamport_budget_across_slots` observes the clean `0xffff_fff2` because the _second account's_ first step is still preflight).

### N2 — CONFIRMED (Info, test-fidelity) — "catchable funding failure" is unreachable on the real runtime; Mollusk e2e asserts an error shape mainnet cannot produce

1. **Location**
   - `crates/pina/src/migration.rs:859-867` — `Preflight::first_step` treats a failed funding transfer as catchable and returns `Err(Custom(1))`.
   - `examples/migrations_program/tests/e2e.rs:669-709` — `mid_chain_funding_failure_rolls_back_every_earlier_step` asserts `Custom(1)` and passes under Mollusk.
2. **Mechanism**. In the real SVM (surfpool embeds Agave), a failed CPI halts the calling program: the same broken-transfer setup yields `InstructionError(0, ProgramFailedToComplete)`, never `Custom(1)`. The catchable branch is dead on-chain; rollback still holds via transaction atomicity.
3. **Exploit scenario**. None — this is a test-oracle divergence. It matters because the e2e suite documents the boundary ("pre-effect failures are typed errors") in a form the chain cannot show, so a future refactor could silently change which failures are typed without any on-chain suite noticing.
4. **Severity justification**. Info.
5. **Fix**. Add one ignored `tests/surfpool` case asserting `ProgramFailedToComplete` + snapshot rollback for the broken-transfer setup (the attack crate's `d2_broke_payer_cannot_fund_growth` is a ready-made template), and note in the executor docs that only _plan-phase_ failures are typed on-chain; the transfer-failure branch exists for host-only execution.

## D4 — uninitialized grown region (M4): verdict on the executor pre-zero

**Setup** (scratch crate `tmp/sweep/scratch-migration/residue-probe/`, own SBF artifact, same program id, deployed into its own surfnet): `pina migrations make` reworked the `State` v1→v2 draft to append `bonus: u64` at `[44..52]` (52 B current). The generated transition was then edited to delete the `data[44..52].fill(0)` line (simulating the author mistake M4 describes) and the manifest's `implementationSha256` was repinned, so the shipped binary contains a transition that leaves `bonus` unwritten. A v1 fixture (43 B) was installed rent-exempt and the reserved route `[FF]` driven with a funded attacker payer (cap raised to 200,000 in the probe so the 62,640-lamport deficit funds — see N1 for what happens at the example cap).

**Result** (dynamic, surfpool = real Agave SVM):

```
D4 committed account (52 bytes): [01, 02, <authority>, 64 00.., 01, 00, 00 00 00 00 00 00 00 00]
D4 committed bonus bytes: [00, 00, 00, 00, 00, 00, 00, 00]
```

`bonus == 0`. The runtime zero-fills the grown region, so the unwritten byte range commits zeros, passes `validate_migration_destination` (u64 has no range validation), and is version-stamped — as **zeros**. I additionally traced the allocator path for an attacker-controlled-residue variant (same-instruction shrink-then-grow, the classic realloc stale-data pattern): within one deployed program a valid stale account's pre-instruction length always equals its exact source size (histories are additive, and the executor's post-step truncate happens only after the transition has run), so every byte the transition _could_ leave unwritten lies beyond any byte this account ever persisted — there is no stale tail to resurrect.

**M4 verdict**: the exploit M4 describes is **not reachable through pina's account executor on this stack** — the zero-fill comes from the runtime, not from pina. The proposed executor pre-zero (fill `[old_len..working_size]` after the growth resize) is therefore **defense-in-depth, not load-bearing**: worth landing because it is cheap (bounded by the 10 KiB growth cap), because it makes "transitions must write every added byte" a hardening rule instead of a runtime dependency, and because it matches what the instruction/event paths already do — but it does not block any downstream program from shipping today, and a forgotten field manifests as a defined zero default, not as attacker data.

## Not executed

- **B1** (reserved route via CPI under a wrong executing id): needs a deployed CPI-caller program; the pre-migrate program-id check is already pinned by the example's host unit test on the exact serialized-input path.
- **E1** (depth-9+ stranding): needs a 10-version scratch history (nine `migrations make` cycles). The runtime gate (`migration.rs:1027-1029`) and the client workaround (drive `[FF]` repeatedly; ≤ 8 adjacent steps per call) are statically established; only the exact stranded-depth boundary was not re-measured.
- D4's same-instruction shrink-then-grow residue variant was closed analytically (see above): pina's additive-only histories plus the executor's step ordering never re-grow after a truncate within one instruction for generated code.
