Solana programs without the framework tax.

Pina gives you macros, typed accounts, and generated clients, then compiles to the smallest binaries of any Solana framework. Compute stays at hand-written cost, and deployed programs evolve through managed ABI migrations.

use pina::*;

declare_id!("GJQcuWrT2f3f4KNuJcXhhwUa1ZQTYbxzzJ1hotzKu8hS");

#[discriminator(entrypoint)]
pub enum CounterInstruction {
    Initialize = 0,
    Increment = 1,
}

#[discriminator]
pub enum CounterAccountType {
    CounterState = 1,
}

// 11 bytes on-chain: discriminator, version, bump, count.
#[account(discriminator = CounterAccountType)]
#[pda(seeds = [SEED_COUNTER, authority: Address], bump = bump)]
pub struct CounterState {
    pub bump: u8,
    pub count: u64,
}
#[instruction(discriminator = CounterInstruction::Increment)]
pub struct IncrementInstruction {}

#[derive(Accounts, Debug)]
pub struct IncrementAccounts<'a> {
    pub authority: &'a AccountView,
    pub counter: &'a mut AccountView,
}

impl<'a> ProcessAccountInfos<'a> for IncrementAccounts<'a> {
    fn process(self, data: &[u8]) -> ProgramResult {
        let _ = IncrementInstruction::try_from_bytes(data)?;
        self.authority.assert_signer()?;

        let mut counter = CounterState::load_pda_mut(
            self.counter, self.authority.address(), &ID,
        )?;
        let next = counter.count.get()
            .checked_add(1)
            .ok_or(ProgramError::ArithmeticOverflow)?;
        counter.count.set(next);
        Ok(())
    }
}

dispatch_entrypoint!(CounterInstruction);

Why Pina

Framework ergonomics, hand-written output.

Macros stay minimal and predictable. The IDL is inferred from the validation code you already write, so payer.assert_signer()? becomes a signer constraint without a second source of truth.

Only in Pina

Managed ABI migrations

Version envelopes, generated transitions, and a publication ledger evolve account and instruction schemas without breaking deployed programs or the clients that read them.

How migrations flow →
  1. v0CounterStatebump · countpublished
  2. v1+ authoritygenerated transitionpublished
  3. v2+ last_updatedclients decode every versioncurrent

no_std, allocation-free

Every on-chain crate compiles to the bpfel-unknown-none SBF target with no heap and no allocator.

Validated zero-copy

PinaPod validates account bytes before Pina hands you an in-place, typed view. No copies, no heap.

One-byte discriminators

Accounts, instructions, and events carry a typed discriminator as their first field, one byte by default and up to u64 when you need it.

Declarative validation

Chain checks on any account, or compile #[pina(validate(...))] rules into allocation-free code.

payer.assert_signer()?
     .assert_writable()?;

Tooling

One CLI from init to mainnet.

Scaffold, build, test, lint, profile, and deploy without leaving pina. Commands follow documented output contracts, with JSON where it matters, so scripts and coding agents can drive pina as reliably as you can.

Browse the CLI reference →
  • pina lintSecurity lints for common Solana attack patterns, run on program source.
  • pina profileEstimate compute cost from the compiled .so, or trace it per line from tests.
  • pina rehearseReplay real traffic against an upgrade before you ship it.
  • pina explainName the account check that made a transaction fail.
  • pina devAn offline Surfpool loop that rebuilds and redeploys as you edit.
  • pina verifyCompare a deployment with its source and record the verified build.

Get started

Your first program in three commands.

  1. 1

    Install the CLI

    Prebuilt for macOS, Linux, Windows, and FreeBSD. Or cargo install pina_cli.

    npm install --global @pina-rs/cli
  2. 2

    Scaffold a program

    A no_std program, a typed starter instruction, and host and Surfpool tests.

    pina init my_program
  3. 3

    Build and test

    Compile to SBF with the Agave toolchain, then run the scaffold’s tests.

    cd my_program && pina build && pina test
