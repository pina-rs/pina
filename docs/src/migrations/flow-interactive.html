How Pina Migrations Work

A step-by-step guide to versioned, automatic ABI migrations: what you run, what the framework does for you, and what happens on-chain when old data meets a new program.

The short version: you never write a migration by hand for ordinary changes. You change your structs like always and run one CLI command when the build asks. If a field was renamed or removed, you answer one question. The program then carries every old account, instruction, and event forward to the current shape inside whichever transaction touches it. Clients keep working unchanged.

Part 1: the developer journey

Seven steps from turning migrations on to shipping a new version. Click each step to expand it. The under-the-hood panels explain the machinery for anyone curious.

Add a [migrations] section to your program's pina.toml and pick how wide the version counter should be. u8 is fine for almost every program, and distinguishes 256 versions per contract.

$ cat pina.toml [project] program = "." [migrations] version-type = "u8"
What happens under the hood

Accounts, instruction payloads, and events all gain a version envelope. The version number sits immediately after the existing discriminator. The framework owns these bytes, so your code never reads or writes them by hand.

The encoding (u8, u16, or u32) is program-wide, so every contract shares one envelope size. Generated code picks the matching implementation, not you.

Nothing special here, and that is the point. Say your State account needs a new revision counter:

// v1: authority + value // v2: authority + value + revision ← your change

You do not write a conversion function, bump a constant, or touch stored data. Just edit the struct.

$ pina build error: State changed since the recorded schema (v1). Its data schema or instruction process ABI changed. Run `pina migrations make` and review the transition.

You cannot ship a wire-format change without a migration. The build refuses until the change is recorded, and CI runs the same gate through pina migrations check.

What happens under the hood

The derive macros snapshot each contract's schema (field names, types, order, layout) at compile time and compare it against a checked-in manifest. When the code and the manifest disagree, you get the compile error you just saw.

$ pina migrations make contract `state`: appended field `revision: u8` → automatic transition generated (zero-fill new field) ✓ recorded version 2 for state

Most changes need nothing from you. Appending fields, growing fixed buffers, and widening numbers produce a generated transition with no input.

Two kinds of change ask a question:

? field `value` (type `u64`) is removed for `state`. was `value` renamed to `balance` (type `u64`)? [y] rename, preserve the stored data [n] remove, discard the stored data and zero-fill `balance`

On a terminal you answer interactively. In CI or an agent, the same questions arrive as JSON, or as a failure that names the flag to run:

$ pina migrations make --json stdout: [{"contract":"state","from":"value","to":"balance","rustType":"u64"}] stderr: error: ambiguous field changes need an explicit answer - `state`: was `value` renamed to `balance` (type `u64`)? answer with --rename value:balance, or --assume-removed value $ pina migrations make --rename value:balance # non-interactive answer
Removing a field always needs an explicit yes. You confirm interactively, or pass --assume-removed. Every dropped field also prints a warning naming what was discarded.
What happens under the hood

Two files change. migrations/manifest.json records the new version and its full schema snapshot. migrations/transitions/account_1_03/… holds a generated Rust transition that copies overlapping bytes field by field and zero-fills anything new.

migrations/ ├── manifest.json ← every version's schema, per contract ├── publications.json ← hash-chained release ledger (step 6) └── transitions/ ├── account_1_02/ ← v1 → v2 for the State account ├── instruction_1_00/ └── event_1_04/

Renames are recorded as byte-preserving moves. If a new answer ever contradicts recorded history, the CLI rejects it instead of guessing.

Some changes have no safe automatic answer, like changing a field's type or moving an account from fixed to compact layout. The CLI still records the migration, but generates the transition with a failing todo!() body so the build will not let you forget it:

// TODO: convert the stored representation (runs on-chain, must be infallible) fn migrate(source: &[u8], destination: &mut [u8]) { // read v1 field → convert → write v2 field }

pina migrations check fails while any TODO remains, so CI can enforce completion. Everything around your body stays framework-owned: validating the old bytes, validating the result, the version bump, the rent math.

$ pina build $ pina deploy --record-publication --program-id <ID> ...
What happens under the hood

Deploy appends a receipt to publications.json recording which ELF bytes went on-chain, which manifest versions they carried, and the hash of the previous receipt. Each receipt is hash-chained to the last, so the history cannot be edited or reordered later.

Once a version is published it becomes immutable. Its schema snapshot and transition files are frozen, and any later edit to them fails pina migrations check. Shipped migrations are history, not drafts. If a deploy dies halfway, pina migrations reconcile inspects the pending receipt and either completes it or abandons it explicitly. An abandoned receipt still freezes whatever shipped.

$ pina generate ✓ typescript → clients/typescript ✓ rust → clients/rust ✓ cpi → clients/cpi

Every generated encoder stamps the current version into the envelope automatically. Your client code constructs instructions and decodes accounts exactly as before.

Old clients keep working. A client built before the migration still writes version 1. The program accepts it and normalizes it on-chain (Part 2). You upgrade clients on your own schedule, not in lockstep with deploys.

Part 2: what happens on-chain

Every wire format carries the framework-owned envelope. When a transaction arrives, the program routes on the version byte. This diagram is the entire decision tree.

An old account meeting a new program, step by step

Account migrations are the interesting case because they can change the account's size, and size changes rent. This is what one instruction does when the account is two versions behind.

Who pays? If a migration grows the account, the transaction's payer tops up rent — about 6,960 lamports per byte at the two-year exemption threshold — never more than a per-program cap the developer sets (max_lamports). Shrinking migrations charge nothing and never refund; the lamports stay in the account. The instruction rewrite itself costs compute units in the same transaction, bounded by MAX_INLINE_STEPS and a 1 KiB stack workspace. Generated code does not compile if a payload needs more than that.

Part 3: old clients, new clients, who does what

The division of labor is intentional. Clients write versions. Programs migrate data. A client never rewrites an account and never needs to know a migration exists.

New client → new program

client writes v2 · program knows v2

The everyday case. Bytes already match, so the program validates and runs. Costs exactly what a program without migrations would cost.

FAST PATH

Old client → new program

client writes v0 · program knows v2

The program normalizes the request, and any accounts it touches, inline in the same transaction. The old client just sees the transaction succeed.

JUST WORKS

New client → old program

client writes v2 · program knows v0

The version is from the program's future, so it fails with a clear version error instead of misreading bytes. Deploy the new program first. A client ahead of its program always fails loudly, never with a silent misread.

FAILS LOUDLY

Classic behavior, untouched. Migrations only change things when the program is ahead of the data.

Migrating read-only accounts: the sweep instruction

Migration needs a writable account, since it rewrites bytes and may resize. So a stale account that your program only reads will fail its load with a "migration required" error until one transaction touches it as writable. The clean fix is a small instruction whose only job is migrating.

You can write this instruction by hand today, and it takes one of two shapes. Either one migration instruction per account, or one catch-all instruction where every migratable account appears as an optional, writable view, plus a payer. The catch-all is usually the better deal: optional views already give you per-account granularity, because the client simply omits the accounts it does not need. A typical program ends up with:

// one instruction, every migratable account optional and writable instruction migrate_accounts { payer AccountMeta // writable + signer, usually the transaction fee payer escrow Option<AccountMeta> // writable user_profile Option<AccountMeta> // writable stake Option<AccountMeta> // writable }
// the handler is a straight line of independent sweeps if let Some(view) = accounts.escrow { MigrateAccount { account: view, payer: Some(accounts.payer), program_id, max_lamports, } .invoke::<Escrow>()?; } // ...same for each account. Absent accounts are skipped. // Already-current accounts return early and write nothing.

The client sends this instruction first, then the real one, in the same transaction:

$ transaction: [ migrate_accounts(escrow, user_profile, payer) , swap(...) ]
Why this is safe to expose. The sweep only moves accounts forward through published transitions, and each account is checked to be owned by your program before anything happens. It is idempotent: current accounts cost one envelope read and write nothing, so the client can send it speculatively without wasting budget. The payer only ever adds lamports to an account, never removes any, and only up to the max_lamports cap the developer sets. And since each caller supplies its own payer, nobody can be made to fund someone else's migration.
CaseWhat the sweep does
Account absent (client omitted it)Skipped entirely
Already currentOne envelope read, no writes, no rent, near-zero compute
Stale, same sizeRewritten in place, version committed
Stale, growingPayer tops up the rent deficit (capped by max_lamports), account resized, then rewritten
Stale, shrinkingRewritten and shrunk. Lamports stay in the account; there is no refund today
Any step failsWhole transaction rolls back, including every earlier sweep in the same instruction

Two details are worth calling out. On refunds: shrinking keeps every lamport in the account by design. Refunding would mean picking a recipient when the funder and the owner differ, and it would add a transfer per step. A refund-to-payer variant could exist later, but the current rule is simple and safe: money only ever moves inward. And on surplus bytes: they stay on the account, exactly as stored.

What the framework would add to this pattern. Nothing blocks hand-rolling it today. What a framework-level version adds is a reserved discriminator so the instruction can never collide with a user instruction, a generated handler and client helper so no instruction is hand-written at all, and a client-side staleness check so the helper is only sent when an account is actually behind. That is the Migrate instruction described above, and this sweep is its hand-rolled form for programs that want extra policy in the handler.

Limits and guarantees

Hard limits, and all of them fail cleanly. At most MAX_INLINE_STEPS adjacent versions are walked in one instruction. The normalization workspace is capped at 1 KiB of stack, and generated code does not compile past that. Growth is capped by MAX_PERMITTED_DATA_INCREASE per step and by the payer's max_lamports budget overall. Exceeding any of these fails the transaction. It never silently skips a migration.
The ledger proves history, not identity. publications.json is SHA-256-chained and freezes on publish, so accidental drift cannot slip through. It is not a signature scheme: anyone with write access to the repo can regenerate it. Treat it as a build-time integrity check, not as proof of what happened on-chain.

The reserved Migrate instruction

Pina reserves the all-ones value of every instruction discriminator width for a framework migration instruction, and #[discriminator] rejects user variants that claim it at compile time. A program with migratable accounts routes it before parsing its own enum:

// data: [0xff] — no payload // accounts: [payer, systemProgram, state?, …] if is_migrate_instruction(data) { return process_migrate(program_id, accounts); }

Slot 0 is a writable payer funding the rent deficits (or the program address when no step needs funding), slot 1 is the system program the transfers invoke, and every later slot is a program-owned, self-describing account. A slot holding the program address, or an index past the end of the list, is skipped — so a client sends only the accounts it needs to migrate. MigrateContext validates ownership, rejects duplicated slots, migrates each slot at most once, and applies the same step, growth, and lamport caps as the inline path.

That is the client flow the sweep section below describes, now with a framework-owned entry point: prepend [Migrate { payer }, …real instructions] and the payer authorizes exactly the migration cost.

Generated client helpers

The TypeScript, Dart, and Rust clients generate the pieces of that flow so you never compose metas by hand. Each migratable account module gains the generic needsMigration envelope check as a per-account helper (stateNeedsMigration(bytes) for a State account) — true only when the bytes name this account's discriminator and a version older than the client's schema — plus a <Account>MIGRATION_VERSION constant. Each program gains a Migrate composer whose migratable slots are all optional: omitted slots become program-address placeholders and trailing omitted slots are truncated, so a client sends only the accounts it needs.

const { data } = await fetchEncodedAccount(rpc, address); if (stateNeedsMigration(data)) { await send(getMigrateInstruction({ state: address, payer }).make()); } // now decode `state` and send the real instruction
